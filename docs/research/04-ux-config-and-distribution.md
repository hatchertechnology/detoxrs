## 1. Destructive-operation CLI safety patterns

**Dry-run as default is the emerging norm for rename tools specifically, not universal across all destructive CLIs.**

> **Cross-reference:** this section goes _deep_ on a few tools and _wide across domains_ (terraform, helm, cargo, git, rclone). Doc 23 goes wide _within_ the rename domain — a matrix of ~15 same-domain competitors (nomino, brename, edir, convmv, vidir, qmv, zmv, PowerRename, Advanced Renamer, sanitize-filename and others) that this section never touches, and which in turn does not cover the cross-domain precedents below. Neither section subsumes the other; read both.

- **f2** (Go, the most direct modern competitor) defaults to dry-run/preview. Executing a rename requires the explicit `-x`/`--exec` flag; without it, f2 only prints the preview table. [f2 CLI options](https://f2.freshman.tech/reference/cli-options), [F2 GitHub](https://github.com/ayoisaiah/f2)
- **rnr** (Rust) also defaults to dry-run ("Only show what would be done (default mode)") and requires `-f`/`--force` to write changes. [RnR on Lib.rs](https://lib.rs/crates/rnr), [rnr on crates.io](https://crates.io/crates/rnr) — the crates.io page returns 403 to plain HTTP clients (browser-only); lib.rs is the reliably fetchable mirror. A previously cited version-pinned crates.io URL (`/rnr/0.1.1`) was replaced with the crate root.
- Both confirmed independently — this is a real, deliberate convention among rename-specific tools, not an assumption.
- **git clean** takes the opposite shape: it _refuses to run at all_ without one of `-n` (dry-run), `-f` (force), or `-i` (interactive) — enforced by `clean.requireForce=true` by default. It doesn't default to dry-run so much as it defaults to refusal, pushing the user to explicitly choose preview or force. [Atlassian git clean tutorial](https://www.atlassian.com/git/tutorials/undoing-changes/git-clean), [git clean guide](https://gitcheatsheet.dev/docs/everyday-git/clean/)
- **rclone sync** offers `--dry-run` as an opt-in preview but does not require it; the tool ships guidance to "test first with `--dry-run` or `-i`/`--interactive`" because sync operations can be destructive, but running without any flag executes immediately. [rclone sync docs](https://rclone.org/commands/rclone_sync/), [rclone dry-run guide](https://www.go2share.net/article/rclone-dry-run)
- **sd** (Rust sed-alternative) does not dry-run by default; it offers `-p`/`--preview` as an opt-in confirmation step before an in-place edit. [sd GitHub](https://github.com/chmln/sd), [sd guide](https://kx.cloudingenium.com/en/sd-search-replace-intuitive-find-replace-modern-sed-alternative-guide/)
- **terraform** uses a two-phase pattern rather than a single dry-run flag: `plan` (optionally saved with `-out=FILE`) is reviewed, then `apply` executes that exact saved plan — and Terraform refuses to apply a stale plan if state changed underneath it. This is the strongest "review-then-commit" pattern found and is a plausible model for a rename tool with a "plan file." [terraform apply docs](https://developer.hashicorp.com/terraform/cli/commands/apply), [terraform plan docs](https://developer.hashicorp.com/terraform/cli/commands/plan)
  - **Citation correction (doc 07 row 6, upheld here):** the stale-plan refusal is real, but the `apply`/`plan` doc pages linked above do **not** state it. The behavior is sourced from the "Saved plan is stale" error as discussed on Terraform's own issue tracker — [hashicorp/terraform#21785](https://github.com/hashicorp/terraform/issues/21785), [#25981](https://github.com/hashicorp/terraform/issues/25981) (both re-verified to exist this pass). Cite the issues for the drift-refusal claim and the doc pages only for the two-phase `plan`/`apply -out` mechanics.
- **helm upgrade** layers `--dry-run` (client or server-side simulation) with a roll-back-everything-on-partial-failure flag — a concrete precedent for all-or-nothing semantics on a multi-step operation. **Flag name is version-dependent:** it is `--atomic` in Helm 3, and Helm 4 renamed it to `--rollback-on-failure` with `--atomic` kept as a deprecated alias ([helm/helm#13629](https://github.com/helm/helm/pull/13629)); the rename briefly broke `helm install --atomic` outright ([helm/helm#31900](https://github.com/helm/helm/issues/31900), re-verified this pass). Cite `--rollback-on-failure` as the current name. [Helm upgrade docs (current)](https://helm.sh/docs/helm/helm_upgrade/), [Helm 3 upgrade docs](https://helm.sh/docs/v3/helm/helm_upgrade/) — a third-party Helm-3 walkthrough previously cited here was unreachable (HTTP 000) and has been dropped.
- **cargo publish** has no built-in confirmation prompt at all, and there's a long-standing open issue (#6153) arguing it should be opt-in/confirmed, with a proposed `-y/--yes` bypass modeled on `apt install`. This is a cautionary example of a destructive, irreversible action (crates.io publishes cannot be deleted, only yanked) shipping with _no_ safety rail. [cargo publish should be opt-in, issue #6153](https://github.com/rust-lang/cargo/issues/6153)
- **Non-interactive/no-TTY behavior**: the general pattern across CLIs (Azure CLI, pnpm, etc.) is that any interactive confirmation prompt must have a non-interactive escape hatch (typically `--yes`/`-y`), and tools that need input but detect no TTY should error clearly ("no tty available, use --yes") rather than hang or silently proceed. [Azure CLI TTY issue](https://github.com/Azure/azure-cli/issues/22719)
- **Undo/journal files**: f2 ships `-u`/`--undo`, which undoes the last renaming operation performed in the current working directory. **CONFIRMED (was previously marked unverified in this document — corrected):** f2's own official guide documents the mechanism plainly, one link from the CLI-options page already cited here. After each rename f2 writes a JSON backup into a platform temp directory (`/tmp/f2/backups` on Linux); the filename is the **MD5 hash of the absolute path of the working directory** (e.g. `2b24e38a2a6ba0ee9023bc9b4c2efc19.json`). `f2 -u` must be run from the same directory, and `f2 -ux` deletes the backup after a successful revert. [f2 guide: Reverting a renaming operation](https://f2.freshman.tech/guide/undoing-mistakes.html) — fetched and read directly this pass.
  - **This is a cautionary counter-example, not a precedent to copy.** A temp-dir location is not durable (tmpfs is cleared on reboot; `/tmp` reapers delete it), a hash-only filename is undiscoverable by a user browsing for their own undo history, and it uses no XDG state directory at all. Nothing in Section 2's `XDG_STATE_HOME` recommendation below can be justified with "even f2 already does this" — f2 does the opposite.
- **stdout/stderr discipline**: convention (Heroku CLI style guide, GitHub CLI) is progress/informational output to stderr, result data to stdout, so piping isn't polluted; `--quiet` suppresses progress/spinners; f2's `--quiet` flag changes exit-code behavior on zero matches (exits with an error code instead of success) while continuing to write errors to stderr. [f2 CLI options](https://f2.freshman.tech/reference/cli-options), [Heroku CLI style guide](https://devcenter.heroku.com/articles/cli-style-guide)
- **Per-file failure without aborting**: no source found gave a citable specification for f2's per-file failure handling in a batch (best-effort vs abort-on-first-error) — **unverified, needs direct source inspection**, though the general community convention for bulk operations (rclone, rsync) is best-effort with a non-zero final exit code and a summary of failures, not abort-on-first-error.

**What the evidence shows (observation):** dry-run-by-default with an explicit write gate — `-x`/`--exec` in f2, `-f`/`--force` in rnr — is the established convention among the direct rename-tool competitors, confirmed independently for both. It is not universal across destructive CLIs generally (`rclone sync`, `sd`, `cargo publish` all execute without a gate; `git clean` refuses to run rather than previewing).

**What this document's author recommends (opinion, not evidence):** treat dry-run-by-default as a hard baseline expectation rather than an open option, and evaluate a terraform-style plan-file model so users can apply an _exact_ reviewed plan instead of a re-computed one. The plan-file half is a suggestion by analogy from a different domain, with no rename-tool precedent behind it.

## 2. Config file conventions

### XDG Base Directory Specification — exact paths

Per the [official spec](https://specifications.freedesktop.org/basedir/latest/) and corroborating sources ([ArchWiki](https://wiki.archlinux.org/title/XDG_Base_Directory), [PyXDG docs](https://pyxdg.readthedocs.io/en/latest/basedirectory.html)):

| Variable          | Purpose                                          | Fallback if unset/empty |
| ----------------- | ------------------------------------------------ | ----------------------- |
| `XDG_CONFIG_HOME` | user config                                      | `$HOME/.config`         |
| `XDG_DATA_HOME`   | user data                                        | `$HOME/.local/share`    |
| `XDG_STATE_HOME`  | user state (logs, undo history, etc.)            | `$HOME/.local/state`    |
| `XDG_CACHE_HOME`  | user cache                                       | `$HOME/.cache`          |
| `XDG_CONFIG_DIRS` | system-wide config search path (colon-separated) | `/etc/xdg`              |

Rules: all paths must be absolute; a relative path in any of these variables must be treated as invalid and ignored. `XDG_STATE_HOME` is the natural home for an undo/rename-journal file; `XDG_CONFIG_HOME` for the config file itself.

### Per-project / upward-walking config discovery patterns

Three concrete, well-documented implementations, useful as direct models:

- **ripgrep** deliberately does _not_ auto-discover a config file in any directory. It only reads one if `RIPGREP_CONFIG_PATH` is set (non-empty) to an explicit path; the file is a flat list of CLI arguments (one per line, `#`-comments ignored), effectively pre-selecting flags without any DSL. If the path is set but unreadable, ripgrep errors rather than silently ignoring it. [ripgrep GUIDE.md](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)
- **ruff** walks _upward_ from each file being linted, checking `.ruff.toml` > `ruff.toml` > `pyproject.toml` (in that priority order) at each directory level. The **first match found wins outright — configs are not merged/cascaded** across directory levels unless the user explicitly opts in via an `extend` field pointing at a parent config. [Ruff config discovery](https://docs.bswen.com/blog/2026-03-29-ruff-config-discovery/), [Astral Ruff config docs](https://docs.astral.sh/ruff/configuration/)
- **Prettier** likewise walks upward from the target file to the filesystem root, stops at the first config file found, and — like ruff — does not merge configs across levels (a nested `.prettierrc` fully overrides, doesn't extend, a root one). If two different config file formats exist in the same directory, one is picked by priority and the rest silently ignored. [Prettier configuration docs](https://prettier.io/docs/configuration), [Prettier config resolution issue discussion](https://github.com/prettier/prettier/issues/8303)
- **EditorConfig** walks upward through parent directories collecting `.editorconfig` files, but this one _does_ cascade — closer (deeper) files' matching properties take precedence over farther ones — and stops the walk only when a file sets `root=true` or the filesystem root is reached. [EditorConfig file format spec](https://docs.editorconfig.org/en/master/editorconfig-format.html), [EditorConfig root lookup discussion](https://github.com/editorconfig/editorconfig/issues/376)

These three give a spectrum: ripgrep (opt-in-only, zero discovery magic), ruff/Prettier (auto-discover, first-match-wins, no merge), EditorConfig (auto-discover, cascading merge). All three avoid ever becoming a general-purpose scripting DSL — the config file is data (a set of key/value settings or a flat argument list), never a language with conditionals or expressions.

### Format tradeoffs: TOML vs YAML vs JSON

Not exhaustively sourced in this pass, but the pattern across the exemplars is telling: Rust-ecosystem tools (ruff, Prettier's newer support, most `figment`/`config-rs` consumers) lean TOML for a flat/shallow settings file — no significant whitespace ambiguity (unlike YAML), comments allowed (unlike strict JSON), and a natural fit for `serde`. YAML is common where nesting is deep or human-authors expect it (Prettier still supports it for compatibility with JS-ecosystem norms); JSON is common as a machine-generated/consumed format (e.g., for `--json` output, not hand-authored config). **This sub-point is more inference from the ecosystem than a directly cited claim — flag as lower-confidence.**

### Precedence rules

The general, repeatedly-confirmed layering order across `config-rs`/`figment`-style tools and the exemplars above is: **defaults < system config < user config < project config < environment variables < CLI flags**, i.e., the most specific/most-recently-specified source wins. [config-rs / figment comparison](https://leapcell.io/blog/flexible-configuration-for-rust-applications-beyond-basic-defaults) — this ordering itself is standard 12-factor-app practice reflected in `config-rs`'s design ("environment variables can override file-based configuration, local overrides can override everything"). Ruff and Prettier deviate by _not_ merging project-level configs into user/system ones at all (first-match-wins, full override) — worth noting as an alternate, simpler-to-reason-about model that avoids "which of five files set this value" confusion.

### Named presets/profiles — the maintainer's central ask

**This sub-section was previously the weakest-evidenced claim in the document. It is no longer — the earlier pass simply failed to look outside the rename niche.** No exemplar in the narrow "rename/cleanup" space ships a `--profile web` preset mechanism, but "a flag selects a named block of settings from the user's config file" is a mainstream, heavily-trodden CLI convention with several direct precedents:

- **AWS CLI named profiles** are the closest and strongest analogue, and it is nearly exact. `~/.aws/config` is divided into named sections (`[profile web]`); `--profile web` selects one; a `default` section applies when no profile is named; and individual settings inside the selected profile can still be overridden by environment variables or command-line parameters — the same defaults < config-block < env < flag precedence this document describes in "Precedence rules" above. Fetched and read directly this pass. [AWS CLI: configuration and credential file settings / using named profiles](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-profiles.html)
- **kubectl contexts** are the same idea under a different name: named bundles of settings in a single config file, one marked current, any of them selectable per-invocation with `--context`. [Kubernetes: configure access to multiple clusters](https://kubernetes.io/docs/tasks/access-application-cluster/configure-access-multiple-clusters/)
- **`gcloud` named configurations** — same pattern again, selected by `--configuration` or `CLOUDSDK_ACTIVE_CONFIG_NAME`. [gcloud configurations](https://cloud.google.com/sdk/docs/configurations)
- ripgrep's config-file model supplies the other half of the design: "pre-select flags without a DSL," where the config file is literally a flattened, saved argument list. Combining the two — a `[profiles.web]` TOML table whose keys are the same flag-shaped keys as top-level config, selected via `--profile web` — stays inside the "config = pre-selected flags" model rather than introducing a scripting layer. The **combination** is the part with no direct single-tool precedent; each half is independently well-precedented.
- **Cargo's `[profile.dev]` / `[profile.release]` tables are a weaker, structural-only analogy and are demoted here.** They are TOML-table-scoped named preset groups, and they are familiar to the audience installing a Rust CLI, so the shape will read as idiomatic. But they govern compiler settings rather than arbitrary user flag bundles, they are not selected by a `--profile <name>` flag in the AWS sense (`--profile` names a Cargo profile but the mechanism is build-configuration, not settings-overlay), and **custom named Cargo profiles require an explicit `inherits` key** — a mechanical requirement a flat, non-inheriting preset table would not have. [Cargo Book: profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) — verified this pass, replacing the earlier from-memory assertion.

**What the evidence shows (observation):** ripgrep's flat saved-argument-list config, ruff's and Prettier's first-match-wins upward discovery with no cross-level merge, EditorConfig's cascading alternative, and named-settings-block selection by flag as implemented by AWS CLI / kubectl / gcloud. All of these keep the config file as data; none becomes an expression language.

**What this document's author recommends (opinion, not evidence):** a flat/shallow TOML settings file mirroring CLI flag names 1:1 (ripgrep), upward project-directory discovery with first-match-wins (ruff/Prettier, simpler to reason about than EditorConfig's cascade), and named presets as TOML sub-tables of flag-shaped keys selected by a `--profile`-style flag (AWS CLI's model) — never a template or expression language. The specific choice of first-match-wins over cascading is a judgment call about reasoning cost, not a finding; both models are equally well-precedented.

## 3. Output & observability

- **NO_COLOR** (https://no-color.org/) is a de facto standard: if the env var is set (regardless of value), color output must be suppressed. **CLICOLOR/CLICOLOR_FORCE** is a competing, older, now-largely-deprecated convention where `CLICOLOR=0` disables color and `CLICOLOR_FORCE=1` forces color even when not a TTY. Where both are implemented, `NO_COLOR` takes precedence over `CLICOLOR_FORCE`; absent `NO_COLOR`, `CLICOLOR_FORCE` takes precedence over `CLICOLOR`. Current guidance favors `NO_COLOR` plus the newer `FORCE_COLOR` convention (https://force-color.org/) over `CLICOLOR`. [NO_COLOR vs CLICOLOR discussion](https://users.rust-lang.org/t/enable-or-disable-colored-output-according-to-clicolor--force/4445), [bixense CLICOLOR spec](http://bixense.com/clicolors/)
- **`--json`**: f2 supports a `--json` flag that produces JSON output on stdout while still routing error messages to stderr — a directly-confirmed, citable pattern for exactly this class of tool. [f2 CLI options reference](https://f2.freshman.tech/reference/cli-options)
- General industry convention (Heroku CLI style guide, GitHub CLI issue #1089) is: informational/progress output → stderr; result/data output → stdout; never treat "pretty" human-readable output as a stable scripting contract — a dedicated `--json` mode is the only thing scripts should parse. [Heroku CLI style guide](https://devcenter.heroku.com/articles/cli-style-guide), [GitHub CLI JSON output issue](https://github.com/cli/cli/issues/1089)
- **Quiet/verbose levels**: de facto convention is default = errors/warnings only; `-v`/`--verbose` (repeatable, `-vv`, `-vvv`) escalates to informational then debug output; `-q`/`--quiet` suppresses progress bars and non-essential messages. f2's `--quiet` additionally changes exit-code semantics on a zero-match run (errors instead of success). [f2 CLI options](https://f2.freshman.tech/reference/cli-options)
- **Progress on large trees**: `indicatif` (Rust) is the standard crate for progress bars/spinners with elapsed time, ETA, and position/total — used across the modern-Rust-CLI ecosystem. [Progress bar/verbosity conventions summary](https://www.speakeasy.com/blog/engineering-agent-friendly-cli/)
- **Per-file failures without aborting**: not independently confirmed for f2's exact behavior in this pass (see Section 1) — **unverified** — but the cross-tool convention (rclone, rsync, cargo test runners) is best-effort execution across the batch, per-item error reporting to stderr (or in the `--json` output's error field), and a non-zero exit code at the end summarizing failure count, rather than aborting the whole batch on the first error.

**What the evidence shows (observation):** the `NO_COLOR` > `CLICOLOR_FORCE` > `CLICOLOR` precedence order is specified, not inferred; f2's `--json`-to-stdout / errors-to-stderr split is documented in f2's own reference; the stderr-for-progress / stdout-for-data convention is documented by Heroku and GitHub CLI. Best-effort batch processing is a cross-tool convention only (rclone, rsync, cargo test runners) — **no tool-specific confirmation for f2 was obtained.**

**What this document's author recommends (opinion, not evidence):** implement `NO_COLOR` as primary with `CLICOLOR_FORCE`/`FORCE_COLOR` as secondary force-on signals; ship a `--json` mode using f2's stdout/stderr split; default to best-effort batch processing with a summary exit code rather than abort-on-first-error. The last item rests on convention alone and should be chosen on its merits, not on cited precedent.

**Known coverage gap in this section (not researched, flagged rather than guessed):** this document does not survey signal handling mid-batch (SIGINT/SIGTERM and what happens to a partially-written journal), a structured exit-code taxonomy distinguishing usage error / partial failure / total failure (cf. `sysexits.h`, ripgrep's own exit codes), journal-write-failure ordering, concurrent-invocation semantics, `--print-config`-style config-dump conventions, `--version` output conventions, or i18n of the tool's own messages. Downstream design work needed all of these and had to invent them without a citation from here. Anyone extending this research should start there.

The `rayon`-is-a-poor-fit-for-I/O claim is directionally sourced from general Rust community discussion, **not** from any rename-workload benchmark.

**What this document's author recommends (opinion, not evidence):** `clap` derive + `ignore` crate + `assert_cmd`/`trycmd`/`insta` for tests is a low-risk, high-adoption stack. Treat `rayon` as _not_ obviously justified for the rename operation itself (I/O-bound) — if parallelism is wanted, prototype with a small capped worker pool (or `tokio` if async I/O is otherwise in play) and benchmark with `criterion` before committing to `rayon`; it may still be useful for CPU-bound sub-tasks like computing many regex/transliteration transforms over a large in-memory file list.

## 5. Distribution

- **Release automation**: `cargo-dist` handles the build/package/publish/announce pipeline for multi-platform binaries (installers, checksums, GitHub Release upload); `release-plz` handles versioning/changelog/crates.io publish via a "Release PR" driven by Conventional Commits, and is commonly chained with `cargo-dist` (release-plz tags → cargo-dist builds and uploads artifacts to that tag's GitHub Release). Both are actively maintained (`cargo-dist` 0.32.0, published 2026-05-22, re-verified against the crates.io API this pass), purpose-built for exactly this handoff. [release-plz.dev](https://release-plz.dev/), [cargo-dist on crates.io](https://crates.io/crates/cargo-dist), [orhun's automated Rust releases writeup](https://blog.orhun.dev/automated-rust-releases/)
  - **Naming, corrected:** `cargo-dist` was **rebranded to `dist`** in October 2024, and current documentation and installers use the `dist` branding. The crates.io package that actually installs it is still named **`cargo-dist`**, because the bare `dist` crate name is squatted by an unrelated 2016 placeholder. Expect to see both names in the wild; install `cargo-dist`, read docs written about `dist`. (The rebrand is corroborated by multiple secondary sources and by the tool's own current docs; axo.dev's original announcement post was not directly fetchable, so the rationale — as opposed to the fact — of the rename is unverified.)
- **Static/musl builds**: cross-compiling to `*-unknown-linux-musl` targets (via the `cross` tool or `cargo-zigbuild`) is the standard path to a single, dependency-free Linux binary; several community Docker images (`rust-musl-cross`, `muslrust`, `rust-musl-builder`) exist specifically to simplify this, notably for crates with C dependencies (OpenSSL, etc.) — a rename tool with minimal C deps should have an easier time than those examples. [rust-musl-cross](https://github.com/rust-cross/rust-musl-cross), [cross-compilation and static binaries writeup](https://bugfreeblog.duckdns.org/2023/07/cross-building-and-distributing-static-binaries-in-rust-for-arm-intel-in-ci-for-linux.html)
- **MSRV policy**: convention — sourced here from **hyper's policy page specifically**, not from a survey; the earlier "and broadly cited elsewhere" wording overstated a single citation and has been narrowed — is a rolling window — "always support a Rust stable release at least N months old" (6 months is a commonly cited value) — declared via the `rust-version` field in `Cargo.toml`, verified with `cargo-msrv`, and re-checked after dependency bumps since a transitive dependency can silently raise the effective floor. [hyper MSRV policy](https://hyper.rs/contrib/msrv/), [MSRV RFC](https://rust-lang.github.io/rfcs/2495-min-rust-version.html)
- **Shell completions & man pages**: generate both from the single `clap::Command` definition via `clap_complete` and `clap_mangen` (see Section 4) — this is the standard, drift-free approach in the current Rust CLI ecosystem.
- **Debian/Ubuntu — the real risk flagged by the maintainer's brief is confirmed real**: Debian requires all build-time dependencies to be Debian packages themselves (no network access at build time), so every crate dependency (including transitive ones) must be individually packaged via `debcargo`, each crate becoming its own separate Debian source package with symlinked vendor trees under `/usr/share/cargo/registry/`. This is a substantial, well-documented maintenance burden distinct from a typical Python/Node package — confirmed directly from the Debian Rust Team's own documentation, not inference. [Debian Rust Team packaging tools book](https://rust-team.pages.debian.net/book/packaging-tools.html), [Debian wiki: Rust packaging policy](https://wiki.debian.org/Teams/RustPackaging/Policy), [vendoring Rust deps for a Debian derivative](https://blog.shadura.me/2020/12/22/vendoring-rust-in-derivative/)
  - Practical implication: minimizing the total dependency-tree size (fewer, smaller crates) directly reduces the debcargo packaging burden and is a legitimate design lever, not just a Cargo.lock hygiene concern.
- **Homebrew**: standard path is a formula (Ruby DSL) in a tap repo (`github.com/<user>/homebrew-<name>`) that either (a) shells out to `cargo install --locked --root <prefix>` with `depends_on "rust" => :build` (source build on the user's machine), or (b) — more common for a mature, widely-distributed tool — downloads a prebuilt binary from a GitHub Release and skips the Rust build dependency entirely; getting into **homebrew-core** (no tap needed) requires meeting Homebrew's own inclusion/notability bar. [Homebrew + Rust overview](https://jldlaughlin.medium.com/how-does-homebrew-work-starring-rust-94ae5aa24552), [Homebrew tap mechanics](https://rzero.in/blog/homebrew-tap/)
  - **detox's own Homebrew formula is deprecated.** Verified directly against the Homebrew formula API this pass: `detox` 3.0.1 has `deprecated: true`, `deprecation_date: 2026-07-28`, `deprecation_reason: "unmaintained"`. It is **not yet disabled** — `disabled: false`, and `disable_date` is `null`, i.e. no disable date is published. Homebrew's own practice is to disable a deprecated formula roughly a year after deprecation, which puts a plausible removal around **2027-07-28**; treat that specific date as a **projection from Homebrew policy, not a published field**. (Doc 07 and reviewer L2 both state 2027-07-28 as the formula's "fixed disable date"; that is one year past the published deprecation date and is corrected here.) The consequence either way is the same: detox's macOS distribution channel is already flagged as unmaintained and is on a removal track.
- **Nix**: `pkgs.rustPlatform.buildRustPackage` is the standard nixpkgs helper, taking `pname`/`version`/`src`/`cargoLock.lockFile`; it verifies `Cargo.lock` is in sync with `src` and fails the build otherwise (forces reproducibility); `crate2nix` is a documented alternative for splitting each crate into its own cached derivation on larger dependency trees. [nixpkgs Rust doc](https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/rust.section.md), [packaging a Rust app with Nix walkthrough](https://m7.rs/blog/2022-11-01-package-a-rust-app-with-nix/index.html)
- **Fedora/Arch**: not independently deep-dived in this pass beyond general knowledge — **Fedora uses its own Rust packaging guidelines (similar debcargo-style crate-per-package concerns exist but with somewhat more automation via `rust2rpm`); Arch's AUR/community packaging is comparatively lightweight since AUR/`makepkg` can simply run `cargo build --release` against vendored or network-fetched deps at build time without Debian's no-network constraint. Flag both as needing a dedicated follow-up pass if precision is required — not independently verified with citations in this research round.**

## 6. Migration (options only, no recommendation)

The brief asks for a description of migration **options** and their tradeoffs — not a chosen path. Three axes of compatibility surface fell out of the research:

> **Correction affecting this entire section: there is no live upstream to migrate _from_, and nobody to coordinate with.** `dharple/detox` is archived (`archived=true`, last push 2026-07-12, 446 stars, 0 open issues — re-verified via the GitHub API this pass). This section was originally written assuming a maintained upstream: option C2 below literally reads "detox package maintainers (if any) decide independently whether to deprecate," and options in axis A imply a config grammar that might still evolve. Neither holds. Concretely, this changes three things:
>
> 1. **Migration is one-directional and permanent.** detox's config grammar and flag surface are frozen at v3.0.1; whatever a converter targets today, it targets forever. That makes a one-shot converter (A2) cheaper than it looked and read-compatibility (A1) more clearly overpriced, since there is no upstream drift to track.
> 2. **The coordination options are not available.** Any option premised on upstream agreeing to hand over a name, bless a successor, or publish a pointer is off the table. The only counterparties left are downstream distro packagers.
> 3. **Downstream is where all remaining decisions live, and they are on their own clocks.** detox's Homebrew formula is already deprecated as unmaintained; distro packagers will retire an unmaintained C package on their own schedules. Options C1/C3 therefore describe negotiations with volunteer packagers, not with a project.

**A. Existing `detoxrc`/config file compatibility**

- _Option 1 — Read-compatible_: successor tool parses existing `.detoxrc`/`detox.conf` XML-ish config on first run and offers to translate it into the new flat TOML format. Tradeoff: meaningfully eases migration for existing users with elaborate custom filter chains, but commits the new codebase to carrying detox's legacy config grammar (potentially including exactly the kind of complexity — encoding-table-driven filters — the maintainer's stated direction wants to move away from) as permanent parsing surface.
- _Option 2 — One-shot converter tool/subcommand, then drop support_: ship a `migrate` subcommand that reads old config once and emits new config, with no ongoing support for the old format afterward. Tradeoff: bounds the legacy-parsing burden to a single code path that can eventually be deleted, but means any detox config feature with no equivalent in the new tool becomes a hard migration gap the user must resolve manually at conversion time, and per the maintainer's brief may deliberately have no equivalent (e.g., character-encoding-table filters).
- _Option 3 — No compatibility, docs-only migration guide_: no code reads old config at all; a written guide maps common detox filter chains to new-tool flag equivalents. Tradeoff: simplest for the new codebase, but pushes 100% of migration effort onto users and forfeits the "just works" framing for anyone currently on detox with a non-trivial config.

**B. Muscle-memory / flag compatibility**

- _Option 1 — Flag aliasing_: accept detox's historical short flags as hidden aliases for new-tool equivalents (à la how many rewritten CLIs quietly accept the old tool's most common flags). Tradeoff: reduces day-one friction for detox users' shell history/scripts/aliases, but permanently couples the new flag surface to an old tool's design even where the new tool's own flag naming is more consistent — and the maintainer's brief is explicit about _not_ wanting to inherit unnecessary legacy shape.
- _Option 2 — No flag compatibility, distinct binary name_: new tool is unambiguously a new tool with its own flag conventions from day one, install alongside detox (different binary name) so nothing breaks silently. Tradeoff: cleanest design, avoids "detox but the flags mean something slightly different now" confusion bugs, but means literally zero of detox's muscle memory transfers.

**C. Distro packaging coexistence**

- _Option 1 — Same binary/package name as detox, replaces it_: successor takes over the `detox` package name in distros, positioned as a drop-in upgrade. Tradeoff: users get it "for free" on next system update with no discovery friction, but a same-name replacement with different behavior (especially given the dry-run-by-default shift this research recommends investigating in Section 1) is a well-known source of "my scripts silently started doing something different" incidents. **This risk is now confirmed, not inferred:** detox does _not_ default to dry-run — its README documents `-n`/`--dry-run` as the opt-in flag ("The most important option to learn is `-n`, aka `--dry-run`"), which means the default action renames files, and doc 07 confirmed the same from detox's man page directly. [detox README](https://github.com/dharple/detox/blob/main/README.md) — fetched and read this pass; the earlier "not independently re-verified / implied by the brief" hedge was unnecessarily conservative and is removed. A same-name replacement that flips the default from rename-on-invoke to preview-on-invoke would change the behavior of every existing detox invocation in every user script.
- _Option 2 — New, distinct package name; the detox package is left to its downstream lifecycle_: successor is packaged and discovered as its own thing. Note the correction above: upstream detox is archived, so this is not "detox continues to exist independently" — it is each **distro's** packagers independently deciding when to deprecate an unmaintained package and whether to point users at a successor. Tradeoff: slower adoption curve, no "free" upgrade path via `apt upgrade`, but zero risk of silently changing behavior under an existing script's feet, and sidesteps the trademark-uncertainty flagged in Section 5.
- _Option 3 — Provides/Conflicts relationship in packaging metadata_: successor is a separate package that distros can optionally configure to `Provides: detox` / `Conflicts: detox`, letting downstream distro maintainers (not the upstream project) decide the replacement posture per-distro. Tradeoff: pushes the hardest decision to volunteer distro packagers, who may make inconsistent choices across distros — but keeps upstream from having to make one universal call.

No source found directly addresses this specific migration-strategy question (it's a project-planning decision, not something citable from an exemplar tool) — this section is options-generation from the general packaging/compatibility patterns observed elsewhere in this research, not a sourced finding.
