# UX, Safety, and Distribution Expectations for a Modern Rust Bulk-Rename CLI

Evidence base for a `detox` successor. This document supplies findings and citations only — no design proposal, no tool name, no final recommendation on trade-offs presented as options (section 6).

---

## 1. Destructive-operation CLI safety patterns

**Dry-run as default is the emerging norm for rename tools specifically, not universal across all destructive CLIs.**

- **f2** (Go, the most direct modern competitor) defaults to dry-run/preview. Executing a rename requires the explicit `-x`/`--exec` flag; without it, f2 only prints the preview table. [f2 CLI options](https://f2.freshman.tech/reference/cli-options), [F2 GitHub](https://github.com/ayoisaiah/f2)
- **rnr** (Rust) also defaults to dry-run ("Only show what would be done (default mode)") and requires `-f`/`--force` to write changes. [rnr on crates.io](https://crates.io/crates/rnr/0.1.1), [RnR on Lib.rs](https://lib.rs/crates/rnr)
- Both confirmed independently — this is a real, deliberate convention among rename-specific tools, not an assumption.
- **git clean** takes the opposite shape: it *refuses to run at all* without one of `-n` (dry-run), `-f` (force), or `-i` (interactive) — enforced by `clean.requireForce=true` by default. It doesn't default to dry-run so much as it defaults to refusal, pushing the user to explicitly choose preview or force. [Atlassian git clean tutorial](https://www.atlassian.com/git/tutorials/undoing-changes/git-clean), [git clean guide](https://gitcheatsheet.dev/docs/everyday-git/clean/)
- **rclone sync** offers `--dry-run` as an opt-in preview but does not require it; the tool ships guidance to "test first with `--dry-run` or `-i`/`--interactive`" because sync operations can be destructive, but running without any flag executes immediately. [rclone sync docs](https://rclone.org/commands/rclone_sync/), [rclone dry-run guide](https://www.go2share.net/article/rclone-dry-run)
- **sd** (Rust sed-alternative) does not dry-run by default; it offers `-p`/`--preview` as an opt-in confirmation step before an in-place edit. [sd GitHub](https://github.com/chmln/sd), [sd guide](https://kx.cloudingenium.com/en/sd-search-replace-intuitive-find-replace-modern-sed-alternative-guide/)
- **terraform** uses a two-phase pattern rather than a single dry-run flag: `plan` (optionally saved with `-out=FILE`) is reviewed, then `apply` executes that exact saved plan — and Terraform refuses to apply a stale plan if state changed underneath it. This is the strongest "review-then-commit" pattern found and is a plausible model for a rename tool with a "plan file." [terraform apply docs](https://developer.hashicorp.com/terraform/cli/commands/apply), [terraform plan docs](https://developer.hashicorp.com/terraform/cli/commands/plan)
- **helm upgrade** layers `--dry-run` (client or server-side simulation) with `--atomic` (roll back *all* resources if any part of the upgrade fails) — a concrete precedent for all-or-nothing semantics on a multi-step operation. [Helm upgrade docs](https://helm.sh/docs/v3/helm/helm_upgrade/), [Helm 3 upgrade command guide](https://devopsbyexample.io/helm-3-upgrade-command-dry-run-rollback-atomic-cleanup-on-fail-force-and-more/)
- **cargo publish** has no built-in confirmation prompt at all, and there's a long-standing open issue (#6153) arguing it should be opt-in/confirmed, with a proposed `-y/--yes` bypass modeled on `apt install`. This is a cautionary example of a destructive, irreversible action (crates.io publishes cannot be deleted, only yanked) shipping with *no* safety rail. [cargo publish should be opt-in, issue #6153](https://github.com/rust-lang/cargo/issues/6153)
- **Non-interactive/no-TTY behavior**: the general pattern across CLIs (Azure CLI, pnpm, etc.) is that any interactive confirmation prompt must have a non-interactive escape hatch (typically `--yes`/`-y`), and tools that need input but detect no TTY should error clearly ("no tty available, use --yes") rather than hang or silently proceed. [Azure CLI TTY issue](https://github.com/Azure/azure-cli/issues/22719)
- **Undo/journal files**: f2 ships `-u`/`--undo`, described as undoing "the last renaming operation performed in the current working directory" — confirmed present, but the exact on-disk format/location of its undo journal was not documented in any source found and should be verified directly from f2's source (`f2/report` or similar package) rather than assumed. **Unverified: exact undo-journal file format/location for f2.**
- **stdout/stderr discipline**: convention (Heroku CLI style guide, GitHub CLI) is progress/informational output to stderr, result data to stdout, so piping isn't polluted; `--quiet` suppresses progress/spinners; f2's `--quiet` flag changes exit-code behavior on zero matches (exits with an error code instead of success) while continuing to write errors to stderr. [f2 CLI options](https://f2.freshman.tech/reference/cli-options), [Heroku CLI style guide](https://devcenter.heroku.com/articles/cli-style-guide)
- **Per-file failure without aborting**: no source found gave a citable specification for f2's per-file failure handling in a batch (best-effort vs abort-on-first-error) — **unverified, needs direct source inspection**, though the general community convention for bulk operations (rclone, rsync) is best-effort with a non-zero final exit code and a summary of failures, not abort-on-first-error.

**Actionable takeaway**: dry-run-by-default with an explicit `-x`/`--exec` (f2) or `-f`/`--force` (rnr) gate is the established convention among direct competitors and should be treated as a hard baseline expectation, not an option to relitigate. A plan-file model (terraform-style) is worth evaluating as a way to let users review then apply an *exact* plan rather than re-computing it.

## 2. Config file conventions

### XDG Base Directory Specification — exact paths

Per the [official spec](https://specifications.freedesktop.org/basedir/latest/) and corroborating sources ([ArchWiki](https://wiki.archlinux.org/title/XDG_Base_Directory), [PyXDG docs](https://pyxdg.readthedocs.io/en/latest/basedirectory.html)):

| Variable | Purpose | Fallback if unset/empty |
|---|---|---|
| `XDG_CONFIG_HOME` | user config | `$HOME/.config` |
| `XDG_DATA_HOME` | user data | `$HOME/.local/share` |
| `XDG_STATE_HOME` | user state (logs, undo history, etc.) | `$HOME/.local/state` |
| `XDG_CACHE_HOME` | user cache | `$HOME/.cache` |
| `XDG_CONFIG_DIRS` | system-wide config search path (colon-separated) | `/etc/xdg` |

Rules: all paths must be absolute; a relative path in any of these variables must be treated as invalid and ignored. `XDG_STATE_HOME` is the natural home for an undo/rename-journal file; `XDG_CONFIG_HOME` for the config file itself.

### Per-project / upward-walking config discovery patterns

Three concrete, well-documented implementations, useful as direct models:

- **ripgrep** deliberately does *not* auto-discover a config file in any directory. It only reads one if `RIPGREP_CONFIG_PATH` is set (non-empty) to an explicit path; the file is a flat list of CLI arguments (one per line, `#`-comments ignored), effectively pre-selecting flags without any DSL. If the path is set but unreadable, ripgrep errors rather than silently ignoring it. [ripgrep GUIDE.md](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)
- **ruff** walks *upward* from each file being linted, checking `.ruff.toml` > `ruff.toml` > `pyproject.toml` (in that priority order) at each directory level. The **first match found wins outright — configs are not merged/cascaded** across directory levels unless the user explicitly opts in via an `extend` field pointing at a parent config. [Ruff config discovery](https://docs.bswen.com/blog/2026-03-29-ruff-config-discovery/), [Astral Ruff config docs](https://docs.astral.sh/ruff/configuration/)
- **Prettier** likewise walks upward from the target file to the filesystem root, stops at the first config file found, and — like ruff — does not merge configs across levels (a nested `.prettierrc` fully overrides, doesn't extend, a root one). If two different config file formats exist in the same directory, one is picked by priority and the rest silently ignored. [Prettier configuration docs](https://prettier.io/docs/configuration), [Prettier config resolution issue discussion](https://github.com/prettier/prettier/issues/8303)
- **EditorConfig** walks upward through parent directories collecting `.editorconfig` files, but this one *does* cascade — closer (deeper) files' matching properties take precedence over farther ones — and stops the walk only when a file sets `root=true` or the filesystem root is reached. [EditorConfig file format spec](https://docs.editorconfig.org/en/master/editorconfig-format.html), [EditorConfig root lookup discussion](https://github.com/editorconfig/editorconfig/issues/376)

These three give a spectrum: ripgrep (opt-in-only, zero discovery magic), ruff/Prettier (auto-discover, first-match-wins, no merge), EditorConfig (auto-discover, cascading merge). All three avoid ever becoming a general-purpose scripting DSL — the config file is data (a set of key/value settings or a flat argument list), never a language with conditionals or expressions.

### Format tradeoffs: TOML vs YAML vs JSON

Not exhaustively sourced in this pass, but the pattern across the exemplars is telling: Rust-ecosystem tools (ruff, Prettier's newer support, most `figment`/`config-rs` consumers) lean TOML for a flat/shallow settings file — no significant whitespace ambiguity (unlike YAML), comments allowed (unlike strict JSON), and a natural fit for `serde`. YAML is common where nesting is deep or human-authors expect it (Prettier still supports it for compatibility with JS-ecosystem norms); JSON is common as a machine-generated/consumed format (e.g., for `--json` output, not hand-authored config). **This sub-point is more inference from the ecosystem than a directly cited claim — flag as lower-confidence.**

### Precedence rules

The general, repeatedly-confirmed layering order across `config-rs`/`figment`-style tools and the exemplars above is: **defaults < system config < user config < project config < environment variables < CLI flags**, i.e., the most specific/most-recently-specified source wins. [config-rs / figment comparison](https://leapcell.io/blog/flexible-configuration-for-rust-applications-beyond-basic-defaults) — this ordering itself is standard 12-factor-app practice reflected in `config-rs`'s design ("environment variables can override file-based configuration, local overrides can override everything"). Ruff and Prettier deviate by *not* merging project-level configs into user/system ones at all (first-match-wins, full override) — worth noting as an alternate, simpler-to-reason-about model that avoids "which of five files set this value" confusion.

### Named presets/profiles — the maintainer's central ask

No exemplar tool in this specific "rename/cleanup" space was found with a first-class `--profile web` style preset mechanism, so this is the weakest-evidenced sub-question and should be treated accordingly. What *is* directly evidenced:

- ripgrep's config-file model already demonstrates "pre-select flags without a DSL": the config file is literally a flattened, saved argument list. A **named-profile** extension of that idea (e.g., a `[profiles.web]` TOML table containing the same flag-shaped keys as top-level config, selected via `--profile web`) is a natural generalization that stays inside the "config = pre-selected flags" model the maintainer described, rather than introducing a scripting layer.
- This matches the general shape of `cargo`'s `[profile.dev]` / `[profile.release]` tables in `Cargo.toml` (a widely-known Rust-ecosystem precedent for named, TOML-table-scoped preset groups, familiar to exactly the audience installing a Rust CLI) — cited from general Rust/Cargo documentation knowledge rather than a specific web source in this pass; **recommend a targeted follow-up search on `Cargo.toml [profile.*]` semantics before relying on this comparison in a design doc.**

**Actionable takeaway**: model the config file as a flat/shallow TOML settings file that mirrors CLI flag names 1:1 (ripgrep's approach), support upward project-directory discovery with first-match-wins (ruff/Prettier's approach, simpler to reason about than EditorConfig's cascade), and represent named presets as TOML sub-tables of flag-shaped keys — never as a template/expression language.

## 3. Output & observability

- **NO_COLOR** (https://no-color.org/) is a de facto standard: if the env var is set (regardless of value), color output must be suppressed. **CLICOLOR/CLICOLOR_FORCE** is a competing, older, now-largely-deprecated convention where `CLICOLOR=0` disables color and `CLICOLOR_FORCE=1` forces color even when not a TTY. Where both are implemented, `NO_COLOR` takes precedence over `CLICOLOR_FORCE`; absent `NO_COLOR`, `CLICOLOR_FORCE` takes precedence over `CLICOLOR`. Current guidance favors `NO_COLOR` plus the newer `FORCE_COLOR` convention (https://force-color.org/) over `CLICOLOR`. [NO_COLOR vs CLICOLOR discussion](https://users.rust-lang.org/t/enable-or-disable-colored-output-according-to-clicolor--force/4445), [bixense CLICOLOR spec](http://bixense.com/clicolors/)
- **`--json`**: f2 supports a `--json` flag that produces JSON output on stdout while still routing error messages to stderr — a directly-confirmed, citable pattern for exactly this class of tool. [f2 CLI options reference](https://f2.freshman.tech/reference/cli-options)
- General industry convention (Heroku CLI style guide, GitHub CLI issue #1089) is: informational/progress output → stderr; result/data output → stdout; never treat "pretty" human-readable output as a stable scripting contract — a dedicated `--json` mode is the only thing scripts should parse. [Heroku CLI style guide](https://devcenter.heroku.com/articles/cli-style-guide), [GitHub CLI JSON output issue](https://github.com/cli/cli/issues/1089)
- **Quiet/verbose levels**: de facto convention is default = errors/warnings only; `-v`/`--verbose` (repeatable, `-vv`, `-vvv`) escalates to informational then debug output; `-q`/`--quiet` suppresses progress bars and non-essential messages. f2's `--quiet` additionally changes exit-code semantics on a zero-match run (errors instead of success). [f2 CLI options](https://f2.freshman.tech/reference/cli-options)
- **Progress on large trees**: `indicatif` (Rust) is the standard crate for progress bars/spinners with elapsed time, ETA, and position/total — used across the modern-Rust-CLI ecosystem. [Progress bar/verbosity conventions summary](https://www.speakeasy.com/blog/engineering-agent-friendly-cli/)
- **Per-file failures without aborting**: not independently confirmed for f2's exact behavior in this pass (see Section 1) — **unverified** — but the cross-tool convention (rclone, rsync, cargo test runners) is best-effort execution across the batch, per-item error reporting to stderr (or in the `--json` output's error field), and a non-zero exit code at the end summarizing failure count, rather than aborting the whole batch on the first error.

**Actionable takeaway**: implement `NO_COLOR` (primary) with `CLICOLOR_FORCE`/`FORCE_COLOR` as secondary force-on signals; ship a `--json` mode with the f2-confirmed stdout/stderr split; default to best-effort batch processing with a summary exit code, not abort-on-first-error (industry convention, not tool-specific confirmation).

|---|---|---|---|
| Arg parsing | `clap` (derive API) | De facto standard; `#[derive(Parser)]`/`#[derive(Subcommand)]`; `global = true` for shared flags across subcommands | [clap derive tutorial](https://docs.rs/clap/latest/clap/_derive/_tutorial/index.html), [clap subcommand patterns](https://dasroot.net/posts/2026/01/building-cli-tools-clap-rust/) |

| Directory traversal | `ignore` crate (used by `ripgrep` and `fd` themselves) over plain `walkdir` | `ignore` wraps `walkdir` internally but adds `.gitignore`/`.ignore`/global-gitignore awareness and a parallel `WalkParallel` iterator; use plain `walkdir` only if gitignore-style filtering is explicitly *not* wanted | [ignore crate docs](https://docs.rs/ignore/latest/ignore/), [ignore vs walkdir comparison](https://speedyleion.github.io/rust/git/2021/02/13/walking-file-directories-in-rust.html) |

| Reversible delete | `trash` crate | Moves files to OS Recycle Bin/Trash cross-platform (Windows/macOS/Linux `os_limited` module); most direct, most commonly cited crate for this need — relevant if the tool ever needs to "trash" a file it's about to overwrite/collide with, distinct from renaming's own undo journal | [trash crate docs](https://docs.rs/trash/latest/trash/index.html) |
| CLI integration testing | `assert_cmd` (single-test ergonomics) + `trycmd`/`snapbox` (bulk `.toml`-driven CLI test suites) | Both actively maintained by the `assert-rs` org; `trycmd` explicitly built for running large collections of CLI tests cheaply | [trycmd announcement](https://users.rust-lang.org/t/ann-trycmd-snapshot-testing-for-a-herd-of-cli-tests/66915), [snapbox GitHub](https://github.com/assert-rs/snapbox) |
| Snapshot testing | `insta` (+ `cargo-insta` for reviewing/accepting diffs) | Widely used for asserting complex output (e.g., a rename-plan preview) against a reference snapshot, with inline-snapshot support | [insta GitHub](https://github.com/mitsuhiko/insta) |
| Property-based testing | `proptest` | 75.7M+ total downloads, latest 1.9.0, actively maintained — well suited to round-trip/idempotence properties (rename(plan) then reverse(plan) == original state) | [proptest crates.io stats](https://generalistprogrammer.com/tutorials/proptest-rust-crate-guide) |
| Benchmarking | `criterion` | 132.5M+ total downloads, actively maintained (David Himmelstrup, Berkus Karchebnyi) | [criterion crates.io](https://crates.io/crates/criterion) |
| Shell completions / man pages | `clap_complete` (completions) + `clap_mangen` (ROFF man pages, typically generated in `build.rs`) | Both are official `clap-rs` org crates, generated directly from the same `clap::Command` definition used for parsing — avoids drift between help text and docs | [clap_mangen crates.io](https://crates.io/crates/clap_mangen), [clap_complete/clap_mangen forum announcement](https://users.rust-lang.org/t/clap-mangen-v0-1-manpage-generation-for-your-clap-applications/71525) |

**Actionable takeaway**: `clap` derive + `ignore` crate + `assert_cmd`/`trycmd`/`insta` for tests is a low-risk, high-adoption stack. Treat `rayon` as *not* obviously justified for the rename operation itself (I/O-bound) — if parallelism is wanted, prototype with a small capped worker pool (or `tokio` if async I/O is otherwise in play) and benchmark with `criterion` before committing to `rayon`; it may still be useful for CPU-bound sub-tasks like computing many regex/transliteration transforms over a large in-memory file list.

## 5. Distribution

- **Release automation**: `cargo-dist` handles the build/package/publish/announce pipeline for multi-platform binaries (installers, checksums, GitHub Release upload); `release-plz` handles versioning/changelog/crates.io publish via a "Release PR" driven by Conventional Commits, and is commonly chained with `cargo-dist` (release-plz tags → cargo-dist builds and uploads artifacts to that tag's GitHub Release). Both are actively maintained, purpose-built for exactly this handoff. [release-plz.dev](https://release-plz.dev/), [cargo-dist on crates.io](https://crates.io/crates/cargo-dist), [orhun's automated Rust releases writeup](https://blog.orhun.dev/automated-rust-releases/)
- **Static/musl builds**: cross-compiling to `*-unknown-linux-musl` targets (via the `cross` tool or `cargo-zigbuild`) is the standard path to a single, dependency-free Linux binary; several community Docker images (`rust-musl-cross`, `muslrust`, `rust-musl-builder`) exist specifically to simplify this, notably for crates with C dependencies (OpenSSL, etc.) — a rename tool with minimal C deps should have an easier time than those examples. [rust-musl-cross](https://github.com/rust-cross/rust-musl-cross), [cross-compilation and static binaries writeup](https://bugfreeblog.duckdns.org/2023/07/cross-building-and-distributing-static-binaries-in-rust-for-arm-intel-in-ci-for-linux.html)
- **MSRV policy**: convention (hyper, and broadly cited elsewhere) is a rolling window — "always support a Rust stable release at least N months old" (6 months is a commonly cited value) — declared via the `rust-version` field in `Cargo.toml`, verified with `cargo-msrv`, and re-checked after dependency bumps since a transitive dependency can silently raise the effective floor. [hyper MSRV policy](https://hyper.rs/contrib/msrv/), [MSRV RFC](https://rust-lang.github.io/rfcs/2495-min-rust-version.html)
- **Shell completions & man pages**: generate both from the single `clap::Command` definition via `clap_complete` and `clap_mangen` (see Section 4) — this is the standard, drift-free approach in the current Rust CLI ecosystem.
- **Debian/Ubuntu — the real risk flagged by the maintainer's brief is confirmed real**: Debian requires all build-time dependencies to be Debian packages themselves (no network access at build time), so every crate dependency (including transitive ones) must be individually packaged via `debcargo`, each crate becoming its own separate Debian source package with symlinked vendor trees under `/usr/share/cargo/registry/`. This is a substantial, well-documented maintenance burden distinct from a typical Python/Node package — confirmed directly from the Debian Rust Team's own documentation, not inference. [Debian Rust Team packaging tools book](https://rust-team.pages.debian.net/book/packaging-tools.html), [Debian wiki: Rust packaging policy](https://wiki.debian.org/Teams/RustPackaging/Policy), [vendoring Rust deps for a Debian derivative](https://blog.shadura.me/2020/12/22/vendoring-rust-in-derivative/)
  - Practical implication: minimizing the total dependency-tree size (fewer, smaller crates) directly reduces the debcargo packaging burden and is a legitimate design lever, not just a Cargo.lock hygiene concern.
- **Homebrew**: standard path is a formula (Ruby DSL) in a tap repo (`github.com/<user>/homebrew-<name>`) that either (a) shells out to `cargo install --locked --root <prefix>` with `depends_on "rust" => :build` (source build on the user's machine), or (b) — more common for a mature, widely-distributed tool — downloads a prebuilt binary from a GitHub Release and skips the Rust build dependency entirely; getting into **homebrew-core** (no tap needed) requires meeting Homebrew's own inclusion/notability bar. [Homebrew + Rust overview](https://jldlaughlin.medium.com/how-does-homebrew-work-starring-rust-94ae5aa24552), [Homebrew tap mechanics](https://rzero.in/blog/homebrew-tap/)
- **Nix**: `pkgs.rustPlatform.buildRustPackage` is the standard nixpkgs helper, taking `pname`/`version`/`src`/`cargoLock.lockFile`; it verifies `Cargo.lock` is in sync with `src` and fails the build otherwise (forces reproducibility); `crate2nix` is a documented alternative for splitting each crate into its own cached derivation on larger dependency trees. [nixpkgs Rust doc](https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/rust.section.md), [packaging a Rust app with Nix walkthrough](https://m7.rs/blog/2022-11-01-package-a-rust-app-with-nix/index.html)
- **Fedora/Arch**: not independently deep-dived in this pass beyond general knowledge — **Fedora uses its own Rust packaging guidelines (similar debcargo-style crate-per-package concerns exist but with somewhat more automation via `rust2rpm`); Arch's AUR/community packaging is comparatively lightweight since AUR/`makepkg` can simply run `cargo build --release` against vendored or network-fetched deps at build time without Debian's no-network constraint. Flag both as needing a dedicated follow-up pass if precision is required — not independently verified with citations in this research round.**
- **detox's current distribution footprint** (the bar to match/beat): confirmed present in Debian, Ubuntu, Linux Mint, and Arch package repositories; Fedora presence was referenced in passing by one source but not independently confirmed with a citable package-repo listing in this pass. [detox GitHub](https://github.com/dharple/detox), [detox on Arch](https://man.archlinux.org/man/detox.1.en), [detox Ubuntu manpage](https://manpages.ubuntu.com/manpages/trusty//man1/detox.1.html) — **a direct Repology query attempt failed in this session (fetch error) and should be retried before finalizing distribution-parity claims.**
- **Naming/trademark**: no specific legal/trademark conflict was found for the string "detox" itself as applied to this niche (file-renaming CLI), but no evidence search surfaced a definitive trademark clearance either — **this needs an actual trademark-database search (e.g., USPTO TESS or equivalent) before any successor name is chosen, not just a web search**, especially given the existing PyPI package `detoxpy` and the pre-existing, unrelated, widely-known "detox" branding in other industries (health/wellness) that a search-engine or app-store listing could collide with. The one directly relevant naming precedent found in the Rust ecosystem is defensive prefixing to avoid shadowing an existing system tool (e.g., `rustc`'s bundled linker being named `rust-lld` rather than plain `lld` to avoid colliding with a system-installed `lld`) — a pattern worth considering if the successor tool's name is at risk of colliding with an existing Unix utility or shell builtin. [rust-lld naming precedent context via Rust trademark policy discussion](https://rustfoundation.org/policy/rust-trademark-policy/)

**Actionable takeaway**: cargo-dist + release-plz is a low-effort, well-precedented release pipeline; prebuilt musl-static binaries should be the primary distribution artifact (GitHub Releases + Homebrew tap + a Nix flake) with Debian/Fedora native packaging treated as a slower-following, higher-effort track — the debcargo burden is real and documented, not speculative, and dependency-tree minimization is a genuine lever to reduce it.

## 6. Migration (options only, no recommendation)

The brief asks for a description of migration **options** and their tradeoffs — not a chosen path. Three axes of compatibility surface fell out of the research:

**A. Existing `detoxrc`/config file compatibility**
- *Option 1 — Read-compatible*: successor tool parses existing `.detoxrc`/`detox.conf` XML-ish config on first run and offers to translate it into the new flat TOML format. Tradeoff: meaningfully eases migration for existing users with elaborate custom filter chains, but commits the new codebase to carrying detox's legacy config grammar (potentially including exactly the kind of complexity — encoding-table-driven filters — the maintainer's stated direction wants to move away from) as permanent parsing surface.
- *Option 2 — One-shot converter tool/subcommand, then drop support*: ship a `migrate` subcommand that reads old config once and emits new config, with no ongoing support for the old format afterward. Tradeoff: bounds the legacy-parsing burden to a single code path that can eventually be deleted, but means any detox config feature with no equivalent in the new tool becomes a hard migration gap the user must resolve manually at conversion time, and per the maintainer's brief may deliberately have no equivalent (e.g., character-encoding-table filters).
- *Option 3 — No compatibility, docs-only migration guide*: no code reads old config at all; a written guide maps common detox filter chains to new-tool flag equivalents. Tradeoff: simplest for the new codebase, but pushes 100% of migration effort onto users and forfeits the "just works" framing for anyone currently on detox with a non-trivial config.

**B. Muscle-memory / flag compatibility**
- *Option 1 — Flag aliasing*: accept detox's historical short flags as hidden aliases for new-tool equivalents (à la how many rewritten CLIs quietly accept the old tool's most common flags). Tradeoff: reduces day-one friction for detox users' shell history/scripts/aliases, but permanently couples the new flag surface to an old tool's design even where the new tool's own flag naming is more consistent — and the maintainer's brief is explicit about *not* wanting to inherit unnecessary legacy shape.
- *Option 2 — No flag compatibility, distinct binary name*: new tool is unambiguously a new tool with its own flag conventions from day one, install alongside detox (different binary name) so nothing breaks silently. Tradeoff: cleanest design, avoids "detox but the flags mean something slightly different now" confusion bugs, but means literally zero of detox's muscle memory transfers.

**C. Distro packaging coexistence**
- *Option 1 — Same binary/package name as detox, replaces it*: successor takes over the `detox` package name in distros, positioned as a drop-in upgrade. Tradeoff: users get it "for free" on next system update with no discovery friction, but a same-name replacement with different behavior (especially given the dry-run-by-default shift this research recommends investigating in Section 1) is a well-known source of "my scripts silently started doing something different" incidents — especially risky since detox itself apparently does *not* default to dry-run today (not independently re-verified against detox's actual current man page in this pass, but implied by the brief's framing of encoding/config complexity as the pain point, not accidental destructive renames).
- *Option 2 — New, distinct package name, detox continues to exist independently or is deprecated separately*: successor is packaged and discovered as its own thing; detox package maintainers (if any) decide independently whether to deprecate/point users at the successor. Tradeoff: slower adoption curve, no "free" upgrade path via `apt upgrade`, but zero risk of silently changing behavior under an existing script's feet, and sidesteps the trademark-uncertainty flagged in Section 5.
- *Option 3 — Provides/Conflicts relationship in packaging metadata*: successor is a separate package that distros can optionally configure to `Provides: detox` / `Conflicts: detox`, letting downstream distro maintainers (not the upstream project) decide the replacement posture per-distro. Tradeoff: pushes the hardest decision to volunteer distro packagers, who may make inconsistent choices across distros — but keeps upstream from having to make one universal call.

No source found directly addresses this specific migration-strategy question (it's a project-planning decision, not something citable from an exemplar tool) — this section is options-generation from the general packaging/compatibility patterns observed elsewhere in this research, not a sourced finding.
